1 Histogram bin accumulation

oblique_apply_projection.cu : 1434   hot path

atomicAdd(&sh_hist[lbl * num_bins + bin], d_ex_dup_counts[example_idx]);

What it does

Each thread in BuildHistogramRandomKernel_2D maps its row's projected value to a bin via cub::LowerBound, then increments the shared-memory histogram for that bin. With 256 threads and 32 bins, ~8 threads contend per bin on average.

Why atomic is used

Multiple threads within the same block can land in the same bin. Without an atomic, concurrent writes to the same shared-memory location produce a race and lost updates. This is the most-executed atomic in the pipeline — called once per active row per projection, per depth.

Measured cost

D1662,83410.6968 thr/bin
D2662,83420.7348 thr/bin
D3662,83440.7858 thr/bin

Total4.015

Can it be avoided? partially

Warp-privatized histograms. Each of the 8 warps in a block maintains its own 32-bin histogram in shared memory (8 warps × 2 classes × 32 bins = 512 ints = 2 KB). Within a warp, threads that hit the same bin use __reduce_add_sync (SM 80+) to sum before a single write — eliminating intra-warp contention entirely. After all warps finish, a single pass merges the 8 per-warp histograms into the final shared histogram with no atomics needed (each thread owns one slot).

Expected improvement: reduces contention from 8-way to zero within each warp, and the merge is a simple sum. On SM 89 (Ada), shared-memory atomics already have ~5-cycle latency, so the gain is moderate — estimated 10–20% on the histogram kernel.

Ballot-based histogram. For each of the 32 bins, every warp executes __ballot_sync(mask, my_bin == b) + __popc. Eliminates atomics entirely but requires 32 ballot rounds per warp — trades atomic latency for instruction count. Only wins if bins are few (≤ 32) and contention is high.

2 Histogram merge to global

oblique_apply_projection.cu : 1447–1448   hot path

if (c0) atomicAdd(&d_hist_class0[off], c0);
if (c1) atomicAdd(&d_hist_class1[off], c1);

What it does

After all threads in a block accumulate into the shared-memory histogram, threads 0–31 merge the block's partial histogram into the global histogram arrays. Multiple blocks may contribute to the same (node, projection) segment.

Why atomic is used

At depth 1 with 1 node, all ~2,589 blocks write to the same segment. Each block's thread 0–31 needs to add its partial bin count to the global total. Without an atomic, concurrent blocks overwrite each other.

Contention

DepthBlocks/segmentContention per bin
D1 (1 node)2,5892,589 blocks
D3 (4 nodes)~647~647 blocks
D5 (16 nodes)~162~162 blocks

Can it be avoided? partially

Two-pass merge. Instead of every block atomicAdd-ing to global, each block writes its per-block partial histogram to a staging buffer (no atomics — each block owns its slot). A second kernel reduces all partial histograms per segment with a tree reduction. Eliminates global atomics entirely but adds a second kernel launch + staging memory (total_node_blocks × 2 × num_bins × sizeof(int)).

At early depths (D1), this would replace 2,589-way contention on 32 bins with a clean tree reduction. At later depths with more nodes, contention drops to ~162 blocks/segment and the atomic is already fast. The if (c0)/if (c1) guards already skip zero-count bins, reducing contention on sparse histograms.

Verdict: The two-pass approach adds complexity (staging buffer allocation, second kernel) for a small gain. Global L2 atomics on SM 89 handle this well. Not worth optimizing unless profiling shows L2 atomic throughput as a bottleneck.

3 Partition position counters

oblique_apply_projection.cu : 290, 293   partition

int pos_idx = atomicAdd(&d_atomic_counters[node_id], 1);      // right-child slot
int neg_idx = atomicAdd(&d_atomic_counters[num_nodes + node_id], 1); // left-child slot

What it does

In SplitExamplesInPlaceKernel, each thread decides whether its row goes left or right based on the split threshold, then atomically claims a write position in the child's segment of d_selected_examples.

Why atomic is used

Classic scatter pattern: all threads in a node race to write to the same two counters. The atomic ensures each row gets a unique position. With ~662K rows and 1 node at D1, all threads contend on a single pair of counters.

Measured cost

Part of partition total: ~0.69 ms/depth (baseline). The DRSW path avoids this kernel entirely.

Can it be avoided? yes

Already avoided in the StablePartition path. StablePartitionCountKernel + StablePartitionScatterKernel (lines 306–427) use a two-pass approach: first a per-block prefix scan to count left/right per block, then a global prefix sum, then a deterministic scatter — no atomics for position assignment. The class-count atomic (site #4) remains in both paths.

The unstable partition (SplitExamplesInPlaceKernel) is the current default because the output order doesn't matter for the histogram. Switching to stable partition eliminates these 2 atomics but adds a second kernel launch and prefix-sum pass. Measured difference is negligible since the two-counter atomic is low-contention (only num_nodes distinct counters, spread across L2 cache lines).

4 Partition class counts

oblique_apply_projection.cu : 299, 422   partition

atomicAdd(&d_class_counts[node_id * 2 * num_classes + side * num_classes + cls],
          d_ex_dup_counts[example_idx]);

What it does

During partitioning (both unstable and stable paths), each thread adds its row's class weight to the appropriate child's class-count bucket. Used to compute leaf-node predictions and to decide whether child nodes are pure (can stop splitting).

Why atomic is used

Many rows share the same (node, side, class) bucket. With binary classification (num_classes = 2), there are only num_nodes × 2 × 2 = 4 × num_nodes distinct counters — high contention at early depths.

Can it be avoided? partially

Warp-coalesced atomics. Use __match_any_sync to group threads with the same (node, side, class) triple, sum within the group via shuffle, and have only the leader atomicAdd. Reduces atomic calls by ~16× (average warp group size). With binary classification, most threads in a warp share the same node and roughly half go to each side, so group sizes are large.

Shared-memory pre-accumulation. Since all threads in a block share the same node (in the 2D kernel), accumulate class counts in shared memory first, then one thread writes to global. Straightforward, adds 4 shared-memory ints per block.

Measured cost: Negligible — only num_nodes × 4 counters, each counter hit by ~82K threads at D1 but L2 atomic coalescing handles this efficiently. The total partition time includes projection reads and scatter writes that dominate. Not a bottleneck.

5 ComputeOffsets position counters

node_id_drsw.cuh : 105   drsw_depth

base_offset = atomicAdd(&d_atomic_counters[nid], group_size);

What it does

In NodeIdDRSW_ComputeOffsetsKernel, each warp finds all threads sharing the same node via __match_any_sync, sums the group, and the leader atomically claims positions for the entire group. This assigns each row a unique node_offset (its position within the node's segment).

Why atomic is used

Multiple warps across different blocks contain rows belonging to the same node. Each warp-group needs a unique range of positions. The atomic counter per node is the synchronization point.

Already optimized

The warp-coalesced pattern (__match_any_sync + leader-only atomic) is the textbook optimization for this pattern. Instead of 1 atomicAdd per thread (~662K atomics), it does 1 per warp-group (~20K–40K atomics depending on node distribution). At depth 1 with 1 node, all 8 threads in a warp share the same node → 1 atomic per 32 active threads.

Measured cost

Total drsw_depth = 0.34 ms across 5 depths (0.07 ms/depth). This includes the memset of counters + kernel launch + sync.

Can it be avoided? yes, but not worth it

Segmented sort + prefix sum. Sort rows by d_node_ids (via cub::DeviceRadixSort), then compute offsets as a simple sequence within each segment. No atomics, fully deterministic. But a radix sort of 1M ints takes ~0.5–1 ms, far more than the current 0.07 ms. Worse.

Verdict: Current warp-coalesced implementation is already near-optimal. The 0.07 ms/depth cost is negligible. Leave as is.

6 SplitUpdate child counters

node_id_drsw.cuh : 261   partition

atomicAdd(&d_child_counters[child_id], 1);

What it does

In NodeIdDRSW_SplitUpdateKernel, each thread decides its row's child node based on the split threshold, writes the new node_ids[row] = child_id, and increments the child's row counter.

Why atomic is used

Many threads map to the same child node. The counter tracks how many rows each child has, which is needed to build node_row_offsets for the next depth.

Can it be avoided? yes

Warp-coalesced atomics. Same __match_any_sync pattern as ComputeOffsets — group threads by child_id, count via __popc, leader-only atomicAdd. Reduces atomic calls by ~16×. With 2 children per split node and 8 nodes at D4, there are only 16 distinct child_ids, so warp groups are large.

Segmented reduction. Alternatively, skip the per-row atomic entirely: after writing node_ids[row], run a separate NodeIdDRSW_CountRows kernel (already exists at line 428) that counts rows per node. This separates the scatter (write node_ids) from the reduction (count per child), at the cost of a second pass over d_node_ids.

Measured cost: Part of partition = 0.37 ms (DRSW). The atomic contention is moderate — only 2 × num_nodes distinct counters. With L2 atomics on SM 89, this is fast. Warp-coalescing would save ~0.02–0.05 ms/depth.

8 FinalMinMax reduction

oblique_apply_projection.cu : 1118–1119, 1183–1184   finMM

atomicMinFloat(&outMin[seg], block_mm.minv);
atomicMaxFloat(&outMax[seg], block_mm.maxv);

What it does

After BlockMinMax produces per-block min/max values, finalMinMaxReduceAtomic merges them into per-segment (node × projection) min/max. Uses CAS-based float atomics since CUDA has no native atomicMin for floats (before SM 90).

Why atomic is used

Multiple meta-blocks contribute to the same segment's min/max. The CAS loop retries until the value is updated.

Contention

At D1 with 1 node: ~2,589 data blocks → ceil(2589/256) = 11 meta-blocks per segment. Only 11 blocks contend per segment — very low. The CAS loop almost never retries.

Measured cost

finMM = 0.01–0.03 ms/depth. Negligible.

Can it be avoided? yes, but pointless

Tree reduction. Replace the atomic merge with a multi-level cub::BlockReduce tree. Since meta-block count is already ≤ 11 per segment, a single block could load all partial results and reduce without atomics. But the current 0.01 ms cost makes this a zero-impact optimization.

9 Bootstrap dedup counts

oblique_apply_projection.cu : 218   one-time

atomicAdd(&d_ex_dup_counts[d_bootstrap[tid]], 1);

What it does

In ComputeBootstrapDupCountsKernel, each bootstrap sample increments the count for its original row index. Builds the d_ex_dup_counts[row] array used by DEDUP_BOOTSTRAP.

Why atomic is used

Bootstrap sampling draws with replacement — multiple samples can reference the same row. The counter must handle collisions.

Measured cost

Part of dedup = 0.49 ms, run once per tree (not per depth). With 662K samples and ~1M rows, contention is very low — most rows are sampled 0–2 times.

Can it be avoided? no need

The bootstrap indices are already sorted. Could use cub::DeviceRunLengthEncode for a non-atomic alternative, but the 0.49 ms one-time cost (which includes sort + unique + memcpy, not just this kernel) is not worth optimizing.

10 CountRows histogram

node_id_drsw.cuh : 437   init only

if (nid >= 0 && nid < num_nodes) atomicAdd(&counts[nid], 1);

What it does

NodeIdDRSW_CountRowsKernel counts how many rows belong to each node, scanning all d_node_ids. Used only during initialization or verification, not on the hot path.

Can it be avoided?

Could use cub::DeviceHistogram or warp-coalesced atomics, but this kernel runs at most once per tree. Not worth touching.

Recommendation

The only atomic worth optimizing is #1 — histogram bin accumulation.

It accounts for ~4 ms out of the ~28 ms depth-loop, and it's the only site where contention is both high (8 threads/bin avg) and on the hot path (every row × every projection × every depth). All other atomics are either already warp-coalesced (#5), low-contention (#3, #4, #6, #7, #8), or one-time costs (#9, #10).

The highest-ROI improvement is warp-privatized histograms: give each of the 8 warps its own 32-bin shared-memory histogram. Threads within a warp accumulate via __reduce_add_sync (single-cycle on SM 80+). After the warp loop, a merge pass sums the 8 partial histograms — 256 threads merging 512 values, zero contention. Shared-memory cost: 8 × 2 × 32 × 4 = 2,048 bytes on top of the existing 256 bytes for splits. Well within the 48 KB shared-memory budget.
